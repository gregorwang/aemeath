# 冗余/复杂度审查报告

> 审查时间: 2026-02-26
> 审查范围: `recorded_paths/`、`characters/sprites/`、`TrajectoryPlayer`、`SpriteAnimator`、`trajectory_recorder` 等相关模块

---

## 一、总体结论

**你的记忆是对的** — 项目的核心功能确实是「按照录制好的轨迹播放角色动画」。但围绕这个简单概念，代码已经膨胀出了大量冗余层和过度设计。以下是具体分析。

---

## 二、`recorded_paths/` 目录分析

### 现状
```
recorded_paths/
├── manifest.json                              (1.9 KB - 轨迹清单)
├── trajectory_1770800738_qt_animation.json    (83 KB - Qt 时间线格式轨迹)
├── trajectory_1771029879.json                 (38 KB - 原始手绘轨迹)
└── trajectory_1771029879_qt_animation.json    (239 KB - Qt 时间线格式轨迹)
```

### 使用情况

| 位置 | 引用方式 | 说明 |
|------|---------|------|
| `Director._resolve_voice_trajectory_path()` | ✅ **使用中** | 搜索 `recorded_paths/` 目录加载轨迹文件 |
| `Director._try_start_voice_scripted_entrance()` | ✅ **使用中** | 创建 `TrajectoryPlayer` 播放轨迹登场 |
| `GifParticleManager.spawn_from_trajectory()` | ✅ **使用中** | 加载并播放轨迹 JSON |
| `trajectory_recorder.py` (工具) | 🔧 独立工具 | 录制轨迹时保存到此目录 |
| `trajectory_to_qt_timeline.py` (工具) | 🔧 独立工具 | 将原始轨迹转成 Qt 动画格式 |

### ⚠️ 问题：路径搜索逻辑极度过度设计

`Director._resolve_voice_trajectory_path()` 方法 (**第 1800–1906 行, 共 106 行**) 实现了一个极其复杂的文件搜索策略：

1. 先检查 **环境变量** `CYBERCOMPANION_TRAJECTORY_PATH`
2. 再搜索 `_base_dir/recorded_paths/`
3. 再搜索 `Path.cwd()/recorded_paths/`
4. 再循环搜索 `_base_dir` 的 **5 层父目录** 的 `recorded_paths/`
5. 再循环搜索 `sys.executable` 的 **5 层父目录** 的 `recorded_paths/`
6. 再搜索 用户数据目录 `user_data_dir/recorded_paths/`
7. 在以上所有 `recorded_paths/` 目录中遍历所有 `trajectory_*.json` 选最新的
8. 最后再 fallback 到直接文件候选列表

**这 106 行代码做的事情，本质上就是：找到 `recorded_paths/` 下的轨迹文件。** 对于桌面应用来说，给一个固定路径 + 一个可选配置项就够了。

### ⚠️ 问题：`manifest.json` 没有被代码使用

`recorded_paths/manifest.json` 定义了轨迹清单（描述、入场方向、触发条件等结构化元数据），但 **代码中完全没有读取这个文件**。`Director` 直接硬编码了 `VOICE_TRAJECTORY_FILE = "trajectory_1771029879_qt_animation.json"`，或者通过遍历目录选最新文件，完全绕过了 manifest。

### 现状

```
characters/sprites/

├── state6_sheet.json  + state6_sheet.png      (487 KB)
└── state7_sheet.json  + state7_sheet.png      (4.4 KB)
```

总共 **~11.9 MB**，其中 `state3_sheet.png` 独占 9.5 MB。

### 使用情况

| 位置 | 引用方式 | 说明 |
|------|---------|------|
| `TrajectoryPlayer._load_sprite_for_state()` | ✅ 有代码 | 在轨迹播放时尝试优先加载 sprite sheet |
| `TrajectoryPlayer._preload_movies()` | ✅ 有代码 | 预加载时优先查找 sprite，找不到才用 GIF |
| `TrajectoryPlayer._update_gif_state()` | ✅ 有代码 | 切换状态时优先使用 sprite |
| `SpriteAnimator` (ui/sprite_animator.py) | ✅ 有代码 | 完整的 sprite 播放器，244 行 |
| `entity_window.py` | ❌ **未使用** | 主角色窗口完全没有用到 sprite |
| `gif_state_mapper.py` | ❌ **未使用** | GIF 粒子系统没有用到 sprite |
| `gif_to_spritesheet.py` (工具) | 🔧 独立工具 | 将 GIF → sprite sheet 的转换工具 |

### ⚠️ 核心问题：Sprite Sheet 系统只在 TrajectoryPlayer 中使用

整个 `SpriteAnimator` 系统（244 行代码）+ `_load_sprite_for_state()` 逻辑 + 11.9 MB 的 sprite 资源，**只服务于一个场景**：轨迹登场动画时优先用 sprite 而非 GIF。

然而：
- **主角色窗口 (`entity_window.py`)** 依然直接用 GIF，从未使用过 sprite
- **GIF 粒子效果 (`gif_state_mapper.py`)** 也完全用 GIF，从未使用过 sprite
- 就连 `TrajectoryPlayer` 本身的 fallback 逻辑也是用 GIF，sprite 只是可选优化

**结论：当前 `characters/sprites/` 是一个「提前做了但没有真正被广泛使用」的功能。** 相当于全套 sprite 资产只用在了轨迹登场这一个触发场景。

## 四、整体复杂度评估

### 调用链分析（语音召唤 → 轨迹登场）

```
用户说唤醒词
  → Director.summon_now()
    → Director._try_start_voice_scripted_entrance()
      → Director._resolve_voice_trajectory_path()        # 106 行搜索逻辑
      → Director._load_trajectory_data()                 # 读取 JSON
      → Director._build_voice_trajectory_gif_map()       # 构建 state→GIF 映射
      → TrajectoryPlayer.__init__()                      # 370 行的播放器类
        → TrajectoryPlayer._preload_movies()             # 预加载 GIF + Sprite
          → TrajectoryPlayer._load_sprite_for_state()    # Sprite Sheet 加载
            → SpriteAnimator.load_from_files()           # 244 行的 Sprite 播放器
        → TrajectoryPlayer.start()
          → QVariantAnimation 驱动
            → _on_timeline_value_changed()
              → _update_frame()                          # 插值位置
              → _update_gif_state()                      # 切换 GIF/Sprite
                → SpriteAnimator.play()/set_flipped()/set_fps()
      → player.finished → Director._on_voice_trajectory_finished()
        → Director._complete_voice_scripted_entrance()
        → Director._cleanup_voice_trajectory_player()
```

**涉及的代码量**：
| 组件 | 行数 | 备注 |
|------|------|------|
| `TrajectoryPlayer` 类 | 370 行 | gif_particle.py 中 |
| `SpriteAnimator` 类 | 244 行 | sprite_animator.py |
| `Director` 轨迹相关方法 | ~170 行 | 路径搜索 + 加载 + 生命周期管理 |
| `trajectory_recorder.py` | 370 行 | 独立录制工具 |
| `trajectory_to_qt_timeline.py` | 330 行 | 格式转换工具 |
| **合计** | **~1484 行** | |

### ⚠️ 与你记忆中的对比

你记得的「调用轨迹」本质上就是：
1. 读取一个轨迹 JSON 文件（一系列 `{x, y, t, s}` 坐标点）
2. 按时间线移动窗口位置
3. 根据 `s` 字段切换显示的 GIF

**这三件事加上合理的错误处理，大概 200 行代码就够了。** 现在膨胀到 ~1500 行，原因：

| 膨胀来源 | 新增复杂度 | 必要性 |
|---------|-----------|--------|
| Sprite Sheet 支持 | +500 行 + 11.9 MB 资源 | ❌ 当前只在 TrajectoryPlayer 用到 |
| 过度搜索路径逻辑 | +106 行 | ❌ 固定路径 + 配置项就够了 |
| 两种 JSON schema 兼容 (`points` vs `keyframes`) | +50 行 | ⚠️ 有一定必要，但应统一 |
| manifest.json | 写了但没用 | ❌ 完全是废代码/废资源 |
| 动态 FPS 调整 | +20 行 | ⚠️ 锦上添花，非必须 |
| GifParticleManager 对 Trajectory 的包装 | +20 行 | ✅ 合理 |

## 五、建议清理方案

### 短期（可以立即清理）

1. **删除 `recorded_paths/manifest.json`**  
   代码完全没有用到它，放着只会造成困惑。

2. **简化 `_resolve_voice_trajectory_path()`**  
   从 106 行缩减到：检查 `_base_dir/recorded_paths/` 即可，最多加一个配置项覆盖。

3. **考虑是否需要 `characters/sprites/`**  
   - 如果决定不用 sprite sheet（主窗口和粒子都没用），可以整个删掉，同时删除 `sprite_animator.py` 和 `TrajectoryPlayer` 中的 sprite 相关逻辑。
   - 如果将来想全面用 sprite，需要同步改造 `entity_window.py` 和 `gif_state_mapper.py`。

### 中期

4. **统一轨迹格式**  
   目前同时支持 `points` 和 `keyframes` 两种 schema，建议统一为一种，删掉转换工具。

5. **考虑将 `trajectory_recorder.py` 和 `trajectory_to_qt_timeline.py` 移出 `src/tools/`**  
   它们是开发时的辅助工具，不应该和运行时代码混在一起。可以移到顶层 `tools/` 目录。
