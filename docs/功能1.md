## 1. 现状分析

### 1.1 切换角色 — 当前能力

| 维度           | 现状                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| **入口**       | 托盘菜单 `切换角色` 子菜单——仅此一个入口                                                     |
| **角色来源**   | `CharacterLoader` 扫描 `characters/` 下的子目录（需含 `manifest.json`、`config.json`、`scripts/dialogue.yaml`、`assets/sprites/peek.png`、`idle.gif/idle.png`） |
| **当前角色包** | 仅 `characters/default/` 一个有效角色包；根目录 `characters/` 下有散落的 `state1~7.gif + aemeath.gif` 作为全局 GIF 资源 |
| **切换逻辑**   | `_switch_character()` 方法：重建 `AssetManager` → 调用 `director.switch_character()` → 更新 `entity_window` 资产根路径 → 刷新预加载 |
| **配置持久化** | 角色选择**不会**写入 `config.json`（当前用 `appearance.theme` 但实际仅在启动时读取一次，运行时切换不回写） |

### 1.2 切换状态 — 当前能力

| 维度           | 现状                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| **状态定义**   | `EntityState` 枚举：`HIDDEN → PEEKING → ENGAGED → FLEEING`（4 个行为状态）                   |
| **GIF 状态**   | `character_states.py` 定义了 8 个 GIF 角色状态 `state1~7 + aemeath`（带标签和表情映射）       |
| **状态切换**   | 完全自动化——由 `Director` + `StateMachine` 根据用户行为、空闲、音频、摄像头等事件自动驱动       |
| **手动控制**   | 用户**没有任何手动切换状态的入口**（只能通过双击/右键间接触发行为状态转换）                     |
| **预览功能**   | 设置面板「动画预览」Tab——展示 7 个 GIF 的预览图 + 触发条件说明 + 行为模式/表情/鼠标映射表（只读） |
| **心情系统**   | `MoodSystem` 0.0~1.0（愤怒↔兴奋），5 档标签，但：<br>- 不影响视觉表现<br>- 不持久化<br>- 用户无法感知当前心情 |

### 1.3 关键发现

1. **角色切换形同虚设**：只有一个角色包（`default`），且角色包的验证规则严格（要求 `manifest.json`、`config.json`、`scripts/dialogue.yaml`、`peek.png`、`idle.gif`），用户几乎不可能自行创建满足规范的角色包。
2. **状态切换完全封闭**：用户完全无法手动控制角色显示哪个 GIF 状态，也看不到当前角色处于什么状态。
3. **预览 Tab 信息过多但无操作性**：5 个分组、大量文字描述，但用户只能"看"不能"用"。
4. **心情系统是死代码**：有完整的增减/衰减逻辑，但产出没有任何可见效果。

## 2. 问题诊断

### 2.1 产品层面的问题

| # | 问题                             | 影响                                        |
|---|----------------------------------|---------------------------------------------|
| 1 | 角色切换入口只有一个且角色包唯一 | 功能等于不存在，用户不知道可以换角色          |
| 2 | 无法自建角色包                   | 用户自定义能力完全断裂                        |
| 3 | 状态不可见、不可控               | 用户无法感知角色当前"是什么情绪/做什么"        |
| 4 | 心情系统无外显                   | 产品宣称有"情感"但用户完全感受不到            |
| 5 | 切换角色不回写配置               | 重启后角色重置，用户困惑                      |
| 6 | 角色包规范过于开发者化           | 用户自己做角色包需要手写 JSON + YAML + 目录结构 |

### 2.2 技术层面的机会

| 已有基础设施                   | 可扩展方向                                    |
| ------------------------------ | --------------------------------------------- |
| `CharacterLoader` 多角色扫描    | 角色包管理 UI                                  |
| `CharacterStateInfo` 有标签系统 | 状态可视化 + 手动切换                           |
| `MoodSystem` 有完整数值逻辑     | 心情可视化 + 持久化 + 影响行为                  |
| GIF 7+1 套完整状态体系          | 皮肤系统 / 换装                                |
| `manifest.json` 角色包元数据    | 角色商店 / 导入导出                             |
| `scripts.json` 台词系统         | 角色专属台词 + 性格定义                         |

用户想要更多角色可选，而不仅仅是内置的 "Default Companion"。

### 产品方案

## 6. 扩展方案四：角色性格系统 (Persona)

### 需求描述

不同角色应该有不同的"性格"——话多/话少、温柔/毒舌、主动/被动。这影响：说话频率、台词风格、互动反应。

### 产品方案

#### 6.1 性格预设

在角色的 `config.json` 中增加 `persona` 配置块：

```json
{
  "persona": {
    "talkativeness": 0.7,       // 0.0=沉默寡言 ~ 1.0=话多
    "warmth": 0.8,              // 0.0=毒舌 ~ 1.0=温柔
    "proactiveness": 0.6,       // 0.0=被动 ~ 1.0=主动
    "energy": 0.5,              // 0.0=慵懒 ~ 1.0=元气
    "greeting_style": "casual", // casual / formal / cute / tsundere
    "pronoun": "我"              // 角色自称
  }
}
```

#### 6.2 性格如何影响行为

| 性格维度         | 影响目标                                        |
| ---------------- | ----------------------------------------------- |
| `talkativeness`  | 控制 `auto_dismiss_seconds` 的缩放（话多→多留一会儿） |
| `warmth`         | 影响安慰台词的选择池（温柔→轻声安慰，毒舌→"不哭了，丢人"） |
| `proactiveness`  | 影响 `idle_threshold_seconds` 的倍率（主动→更早出现） |
| `energy`         | 影响 GIF 动画速度偏好（`anim_speed` 基线）           |
| `greeting_style` | 影响出场台词、回来问候的措辞模板                     |

#### 6.3 用户可调

在设置面板角色 Tab 中用滑块调节各维度：

```
性格调节 (仅对当前角色生效)
┌──────────────────────────────────────┐
│ 话多程度:  ──●───────── 较多 (0.7)   │
│ 温柔程度:  ────●─────── 温柔 (0.8)   │
│ 主动程度:  ─────●────── 适中 (0.6)   │
│ 活力程度:  ──────●───── 适中 (0.5)   │
│ 问候风格:  [ 可爱 ▾ ]                │
│                                      │
│ [ 恢复默认性格 ]                      │
└──────────────────────────────────────┘
```

### 技术要点

| 改动文件              | 改动内容                                   | 改动量     |
| --------------------- | ------------------------------------------ | ---------- |
| 新增 `core/persona.py` | Persona 数据类 + 行为修正计算             | ~60 行     |
| `config_manager.py`   | 新增 `PersonaConfig` dataclass            | ~15 行     |
| `director.py`         | 在空闲计时/台词选择/安慰反应中应用 persona 倍率 | ~30 行     |
| `settings_dialog.py`  | 性格调节滑块 UI                             | ~50 行     |

**复杂度**: ⚠️ 中等  
**价值**: 高——让每个角色真正"有个性"

## 7. 扩展方案五：心情可视化 + 持久化

### 需求描述

`MoodSystem` 已有完整逻辑但完全"看不见"。让用户感知角色心情的变化。

### 产品方案

#### 7.1 心情指示器

在角色窗口上方显示心情小图标（气泡式）：

```
    😊          ← 心情气泡（浮在角色头顶，随心情值变化）
  ┌──────┐
  │ 角色  │
  │      │
  └──────┘
```

心情图标映射：

| 心情值     | 图标 | 标签 |
| ---------- | ---- | ---- |
| 0.0 ~ 0.2 | 😠   | 愤怒 |
| 0.2 ~ 0.4 | 😒   | 不满 |
| 0.4 ~ 0.6 | 😐   | 平静 |
| 0.6 ~ 0.8 | 😊   | 开心 |
| 0.8 ~ 1.0 | 🤩   | 兴奋 |

#### 7.2 心情影响 GIF 选择

当心情值偏离某一方向时，**自动偏好**对应的 GIF 状态：

| 心情范围   | GIF 偏好倾向                       |
| ---------- | ---------------------------------- |
| < 0.3      | 更常切到 state4（害羞/逃跑）        |
| 0.3 ~ 0.7  | 正常映射                           |
| > 0.7      | 更常切到 state6（开心/问候）         |

#### 7.3 持久化

- 在 `config.json` 的 `behavior` 块中新增 `"mood": 0.5`
- 重启时加载上次心情值
- 每次心情变化时延迟写入（防频繁 I/O）

#### 7.4 状态栏显示

在「状态」通知中加入心情信息：

```
当前状态: 已出场 (ENGAGED)
心情: 😊 开心 (0.72)
空闲时间: 2分钟
```

### 技术要点

| 改动文件              | 改动内容                                   | 改动量    |
| --------------------- | ------------------------------------------ | --------- |
| `mood_system.py`      | 增加持久化接口 + 心情→GIF偏好计算           | ~20 行    |
| `entity_window.py`    | 心情气泡 QLabel（浮在角色上方）              | ~40 行    |
| `director.py`         | 心情变化时通知 UI 更新 + 周期性保存          | ~15 行    |
| `config_manager.py`   | `BehaviorConfig` 增加 `mood: float = 0.5`   | ~5 行     |

**复杂度**: ✅ 简单-中等  
**价值**: 高——让用户感受到角色是"活的"

## 8. 扩展方案六：角色皮肤 / 主题换装

### 需求描述

同一个角色可以有不同的"皮肤"——比如夏天版、冬天版、节日限定。

### 产品方案

#### 8.1 皮肤包结构

在角色目录下增加 `skins/` 子目录：

```
characters/default/
├── assets/sprites/         ← 默认皮肤
├── skins/
│   ├── summer/
│   │   ├── manifest.json   ← {"name": "夏日清凉", "preview": "preview.png"}
│   │   ├── state1.gif      ← 覆盖默认的 state1
│   │   ├── state6.gif      ← 覆盖默认的 state6
│   │   └── preview.png
│   └── winter/
│       ├── manifest.json
│       ├── state1.gif
│       └── ...
├── manifest.json
└── config.json
```

- 皮肤包只需要包含要替换的 GIF，缺失的会 fallback 到默认皮肤
- 每个皮肤有自己的 `manifest.json`（名称 + 预览图）

#### 8.2 UI 入口

```
┌─────────────────────────────────────┐
│ 角色皮肤                             │
│                                     │
│ 当前: 默认                           │
│                                     │
│ [🖼 默认] [🖼 夏日] [🖼 冬日]       │
│ [  ✓  ]  [切换]   [切换]            │
│                                     │
│ [ 📂 导入皮肤包 ]                    │
└─────────────────────────────────────┘
```

#### 8.3 自动换肤（高级）

根据季节/节日自动切换皮肤：

```json
{
  "auto_skin_rules": [
    {"skin": "summer", "date_range": "06-01~08-31"},
    {"skin": "winter", "date_range": "12-01~02-28"},
    {"skin": "halloween", "date_range": "10-25~11-01"},
    {"skin": "default", "date_range": "default"}
  ]
}
```

### 技术要点

| 改动文件             | 改动内容                              | 改动量    |
| -------------------- | ------------------------------------- | --------- |
| `asset_manager.py`   | 增加 skin 覆盖资产解析                 | ~30 行    |
| `entity_window.py`   | `set_skin()` → 重新加载 GIF 资源      | ~15 行    |
| `settings_dialog.py` | 皮肤选择 UI                            | ~50 行    |
| `config_manager.py`  | `AppearanceConfig` 增加 `skin: str`    | ~5 行     |

**复杂度**: ⚠️ 中等  
**价值**: 中——对有多套素材的用户很有吸引力

## 9. 扩展方案七：状态联动增强 — 自定义触发器

### 需求描述

让用户自定义"什么情况下角色会切换到什么状态并说什么话"。

### 产品方案

#### 9.1 自定义触发器配置

在角色的 `config.json` 中支持自定义触发规则：

```json
{
  "custom_triggers": [
    {
      "id": "night_coding",
      "condition": {"time_range": "23:00-05:00", "idle_minutes_gt": 5},
      "action": {
        "state": "state5",
        "text": "这么晚了还在写代码？要不要休息一下？",
        "particle": true,
        "mood_delta": -0.05
      }
    },
    {
      "id": "long_session",
      "condition": {"continuous_active_minutes_gt": 120},
      "action": {
        "state": "state6",
        "text": "你已经连续奋斗两小时了，站起来活动一下吧！",
        "mood_delta": 0.1
      }
    }
  ]
}
```

#### 9.2 可配置条件类型

| 条件类型                    | 说明                               |
| --------------------------- | ---------------------------------- |
| `time_range`                | 时间范围                            |
| `idle_minutes_gt/lt`        | 空闲时间大于/小于 N 分钟             |
| `continuous_active_minutes_gt` | 持续活跃时间大于 N 分钟            |
| `mood_gt/lt`                | 心情值大于/小于某阈值                |
| `app_foreground`            | 特定应用在前台（进程名匹配）          |
| `day_of_week`               | 星期几                              |

#### 9.3 UI 配置

放在台词管理或设置高级页面中：

```
┌──────────────────────────────────────┐
│ 自定义触发器                          │
│                                      │
│ # │ 名称          │ 条件      │ 操作 │
│ 1 │ 深夜提醒       │ 23:00-05  │ ✏️🗑 │
│ 2 │ 久坐提醒       │ 活跃>120m │ ✏️🗑 │
│ + │ [ 添加新触发器 ]│           │     │
└──────────────────────────────────────┘
```

### 技术要点

| 改动文件              | 改动内容                             | 改动量     |
| --------------------- | ------------------------------------ | ---------- |
| 新增 `core/custom_triggers.py` | 触发器引擎：条件评估 + 动作执行  | ~120 行    |
| `director.py`         | 周期性检查自定义触发器                | ~20 行     |
| `config_manager.py`   | 支持 custom_triggers 配置块           | ~30 行     |
| `settings_dialog.py`  | 触发器管理 UI（可选，也可先只支持 JSON 编辑） | ~80 行 |

**复杂度**: ⚠️ 中等偏高  
**价值**: 高——让高级用户可以深度定制角色行为

## 10. 综合评估与优先级排序

### 10.1 评估总表

| 方案                         | 技术复杂度 | 改动量       | 风险 | 产品价值 | 前置依赖              |
| ---------------------------- | ---------- | ------------ | ---- | -------- | --------------------- |
| 方案三：状态预览+手动切换     | ✅ 简单    | ~105 行      | 低   | ⭐⭐⭐   | 无                    |
| 方案五：心情可视化+持久化     | ✅ 简单    | ~80 行       | 低   | ⭐⭐⭐   | 无                    |
| 方案一：角色包管理面板        | ⚠️ 中等   | ~195 行      | 低   | ⭐⭐⭐   | 需要更多角色包         |
| 方案四：角色性格系统          | ⚠️ 中等   | ~155 行      | 中   | ⭐⭐⭐   | 无                    |
| 方案六：皮肤/换装             | ⚠️ 中等   | ~100 行      | 低   | ⭐⭐    | 需要皮肤素材           |
| 方案二：角色创建向导          | ⚠️ 中高   | ~265 行      | 中   | ⭐⭐    | 方案一                |
| 方案七：自定义触发器          | ⚠️ 中高   | ~250 行      | 中   | ⭐⭐⭐   | 无（但建议有性格系统配合）|

### 10.2 推荐实施顺序

```
第一阶段：让"角色和状态"可见可控 (MVP)
────────────────────────────────────────
  ① 方案五 — 心情可视化 + 持久化     ~80 行   (让角色"有感情")
  ② 方案三 — 状态预览 + 手动切换     ~105 行  (让用户"能操控")
  ③ 持久化角色选择                   ~5 行    (切换角色不再重启丢失)
  
第二阶段：让角色"有个性" (差异化)
────────────────────────────────────────
  ④ 方案四 — 角色性格系统            ~155 行  (核心差异化功能)
  ⑤ 方案一 — 角色包管理面板          ~195 行  (为多角色铺路)

第三阶段：让用户"能创作" (UGC)
────────────────────────────────────────
  ⑥ 方案二 — 角色创建向导            ~265 行  (降低自建角色门槛)
  ⑦ 方案六 — 皮肤/换装               ~100 行  (同角色多外观)

第四阶段：让用户"能编程" (高级)
────────────────────────────────────────
  ⑧ 方案七 — 自定义触发器            ~250 行  (深度自定义行为)
```

### 10.3 第一阶段的具体产出

如果现在就开始第一阶段，预估总改动量 **~190 行**，涉及以下文件：

| 文件                    | 改什么                          | 行数  |
| ----------------------- | ------------------------------- | ----- |
| `mood_system.py`        | 持久化接口 + GIF 偏好           | ~20   |
| `entity_window.py`      | 心情气泡 UI                     | ~40   |
| `director.py`           | 心情通知 + 状态预览 + 保存       | ~30   |
| `config_manager.py`     | mood 字段                       | ~5    |
| `settings_dialog.py`    | 动画预览 Tab 增加切换按钮        | ~40   |
| `main.py`               | 右键菜单状态子菜单 + config 回写  | ~35   |
| `tray_icon.py`          | tooltip 更新                    | ~5    |

---

> **结论**：当前「切换角色和状态」的核心问题不是"功能缺失"而是"功能隐形"——角色切换菜单空有其表（只有一个角色），状态系统完全自动化（用户无感知无控制），心情系统是纯后端数值（零外显）。优先做**第一阶段**（心情可视化 + 状态手动切换 + 角色选择持久化），用 ~190 行改动就能让用户明显感觉"角色是活的、可控的"，为后续角色包生态和 UGC 创作打好基础。
