> 📅 分析日期：2026-02-25

## 一、问题描述

你觉得「除了调试空闲入侵、轨迹登场以外，其他效果看起来都一模一样」。  
这不是你的错觉——**问题确实存在**，原因有三个层面：

1. **主角色窗口的 GIF 虽然是 7 个不同文件，但很多场景切换到的 GIF 并不明显不同**（尤其是 state1、state5 可能在视觉上难以区分）
2. **GIF 粒子系统（Particle System）的触发条件大多数在日常使用中很难命中**，你平时看到的效果集中在极少数场景
3. **设置面板中 完全没有 任何地方展示"哪个条件 → 哪个动画"的映射**，用户和开发者都只能看代码猜

下面我把 **三大动画子系统** 的完整对应关系一一列出。

## 二、项目中的三大动画子系统

| # | 子系统 | 核心文件 | 简述 |
|---|--------|---------|------|
| 1 | **主角色 GIF 状态** | `entity_window.py` + `director.py` | 桌面上那个角色窗口显示的 GIF，通过 `set_state_by_name()` 切换 |
| 2 | **GIF 粒子效果** | `gif_particle.py` + `gif_state_mapper.py` | 多个独立小 GIF 窗口从屏幕边缘飞入/飞出，用于氛围渲染 |
| 3 | **窗口位移动画** | `entity_window.py`（peek/enter/flee/summon/roam/probe） | 角色窗口本身的位置动画（滑入、滑出、漫步、探头等） |

另外还有一个特殊子系统：
| 4 | **空闲入侵（Idle Invasion）** | `idle_invasion.py` | 用户长时间不操作后，GIF 角色一个一个铺满屏幕 |
| 5 | **轨迹登场（Trajectory Entrance）** | `gif_particle.py → TrajectoryPlayer` | 角色沿着预录制的路径运动 + 切 GIF 状态 |

### 3.3 EntityWindow 的状态优先级决策

当多个触发条件同时存在时，EntityWindow 通过 `_compose_target_state()` 按以下**优先级从高到低**决定显示哪个 GIF：

```
1. 正在漫步移动中（_moving_active=True）   → state3 (ROAMING)
2. 点击临时覆盖状态（_click_override_state）→ 随机选 state2 或 state6
3. 鼠标悬停中（_hover_active=True）         → state5 (HOVER)
4. 正在探头中（_probe_state_name）          → 随机选 state1 或 state7
5. 基础状态（_base_state_name）             → 由 Director 通过 set_state_by_name() 设置
```

## 四、子系统 2：GIF 粒子效果 —— 完整对应表

GIF 粒子是独立于主角色窗口的小 GIF 窗口，由 `GifStateMapper` 控制生成。

| 触发事件 | 方法名 | 使用的 GIF | 数量 | 持续时间 | 触发条件 |
|---------|--------|-----------|------|---------|---------|
| **角色探头/互动** | `on_peeking()` | state1.gif（curious） | 1 个 | 3 秒 | FSM状态→PEEKING |
| **角色进入互动** | `on_engaged()` | state2.gif（excited） | 2 个 | 4 秒 | FSM状态→ENGAGED（屏幕评论期间跳过） |
| **角色逃跑** | `on_fleeing()` | state4.gif（shy） | 3 个 | 2 秒 | FSM状态→FLEEING |
| **角色隐藏** | `on_hidden()` | — | — | — | FSM状态→HIDDEN，清除所有粒子 |
| **语音唤醒/召唤** | `on_summoned()` | state6.gif（greeting） | 3 个 | 5 秒 | 轨迹登场完成后 |
| **长时间空闲** | `on_prolonged_idle()` | state5.gif + state7.gif | 2 个 | 6 秒 | 用户空闲超过 10 分钟 |
| **检测到系统音频** | `on_audio_started()` | state3.gif（music_vibe） | 2 个 | 8 秒 | AudioOutputMonitor 检测到音频开始播放 |

| **音频停止** | `on_audio_stopped()` | — | — | — | 停止脉动定时器 |
| **悲伤安慰** | `on_sad_comfort()` | state5.gif（thinking） | 2 个 | 5 秒 | 摄像头检测到持续悲伤表情 |
| **用户回来** | `on_user_return()` | state6.gif（greeting） | 2 个 | 4 秒 | 摄像头检测到用户离开后回来 |

## 六、子系统 4 & 5：空闲入侵与轨迹登场

### 6.1 空闲入侵（Idle Invasion）

- **触发条件**：用户空闲超过配置的阈值（由 `IdleInvasionConfig` 控制）
- **效果**：直接使用 `state1~state7.gif` 作为粒子，从屏幕四边一个一个冒出来，逐渐铺满屏幕的网格
- **每个入侵者是一个独立的 `GifParticle` 窗口**，随机选择一个 GIF
- **用户有操作时全部撤退**
- ✅ 这个效果**确实和其他所有效果不同**，因为它会生成大量独立窗口铺屏

### 6.2 轨迹登场（Trajectory Entrance）

- **触发条件**：`scripted_entrance_enabled=True` 时自动在召唤时使用，或手动调试触发
- **效果**：角色沿预录制的轨迹（JSON 文件中的关键帧）在屏幕上移动，同时根据轨迹数据中的状态 ID 切换 GIF
- 使用 `TrajectoryPlayer`，可以在轨迹的不同阶段播放不同的 `state1~state7.gif`
- ✅ 这个效果**确实独特**，因为有明确的运动路径和多状态切换

## 七、⭐ 为什么你觉得"效果都一样"— 根因诊断

### 7.1 根因 1：大部分 GIF 切换发生在你看不到的时候

| 状态切换 | 你能看到吗？ | 原因 |
|---------|------------|------|
| ENGAGED 时设置 state1 | 能看到，但这是默认状态 | 角色一出场就是 state1 |
| FLEEING 时设置 state4 | **极难注意到** | 逃跑动画只有 300ms，瞬间就跑掉了 |
| MEDIA_PLAYING → state3 | **难以触发** | 需要系统级音频检测生效，且角色当时必须可见 |
| 被动陪伴/深睡 → state5 | **需要摄像头** | 需要摄像头功能启用并授权 |
| 表情追踪 → state1/4/5/6 | **需要摄像头** | 需要摄像头实时运行 |
| 悲伤安慰/用户回来 → state5/6 | **需要摄像头** | 需要摄像头检测到人脸和表情 |

**结论**：如果你没有启用摄像头功能，你能看到的 GIF 切换基本只有：
- `state1`（99% 的时候）
- `state4`（逃跑，但速度太快看不清）
- `state3`（漫步时会短暂切换，但如果没有自主行为也看不到）

### 7.2 根因 2：GIF 粒子效果的触发条件大多很苛刻

- `on_peeking()` → 几乎不会被调用（当前代码中 Director 没有单独触发 PEEKING 状态的场景，而是直接从 HIDDEN→ENGAGED）
- `on_engaged()` → 只在状态机切换时触发，且屏幕评论时跳过
- `on_audio_started()` → 需要 `AudioOutputMonitor` 正确检测到系统音频、且非自身播放、且非屏幕评论期间
- `on_prolonged_idle()` → 需要用户空闲 10 分钟以上且角色处于 HIDDEN 状态
- `on_sad_comfort()` / `on_user_return()` → 需要摄像头

所以**日常你能看到的粒子效果基本只有：**
- `on_engaged()` 产生的 2 个 state2.gif 粒子（角色出场时）
- `on_fleeing()` 产生的 3 个 state4.gif 粒子（角色逃跑时）

### 7.3 根因 3：命名混乱导致认知困难

三个文件对同一个 GIF 的"语义"定义完全不一致：

| GIF | character_states.py | gif_state_mapper.py | entity_window.py |
|-----|--------------------|--------------------|-----------------|
| state1 | 默认/中性 | 好奇/探头 | STATE_IDLE（空闲） |
| state2 | 行走 | 兴奋/活跃 | STATE_EXCITED（兴奋） |
| state3 | 思考/等待 | 律动/跟随音乐 | STATE_ROAMING（漫步） |
| state4 | 生气 | 害羞/逃跑 | STATE_FLEE（逃跑） |
| state5 | 悲伤/观察 | 思考/发呆 | STATE_HOVER（悬停） |
| state6 | 开心 | 开心/打招呼 | STATE_GREETING（问候） |
| state7 | 惊讶/特殊 | 微型装饰 | STATE_AMBIENT（环境） |

### 7.4 根因 4：设置面板完全没有展示动画映射

`settings_dialog.py` 中**没有任何地方**展示"哪个条件对应哪个动画"。它只有：
- 通用设置（空闲阈值、自动消失时间等）
- AI 设置（API、模型等）
- 语音/视觉设置（摄像头、语音唤醒等）

用户完全无法在 UI 中看到动画映射关系。

## 十、关于"是否应该有一个面板显示状态-动画映射"的建议

**是的，完全应该有。** 以下是建议的实现方式：

### 10.1 在设置面板中增加"动画预览"标签页

建议新增一个 Tab，包含以下内容：

#### A. GIF 状态预览区

```
┌──────────────────────────────────────────────────────┐
│  [动画状态预览]                                        │
│                                                      │
│  state1 (默认/中性)   [GIF预览] ← 当前基础状态         │
│  state2 (兴奋/活跃)   [GIF预览] ← 点击角色时            │
│  state3 (律动/音乐)   [GIF预览] ← 检测到系统音频时      │
│  state4 (逃跑/害羞)   [GIF预览] ← 角色逃跑时            │
│  state5 (思考/观察)   [GIF预览] ← 鼠标悬停/屏幕评论时    │
│  state6 (开心/问候)   [GIF预览] ← 被召唤/用户回来时      │
│  state7 (环境装饰)    [GIF预览] ← 探头侦查时            │
│                                                      │
│  [实际触发条件详细说明...]                              │
└──────────────────────────────────────────────────────┘
```

#### B. 触发条件映射表

一个只读表格，显示本文档第三~六节的内容，让用户清楚知道"什么时候会看到什么"。

#### C. 手动触发按钮

允许用户在预览面板中直接触发每一个动画效果，而不仅仅通过托盘的调试菜单。

### 10.2 统一 GIF 语义命名

应该统一 `character_states.py`、`gif_state_mapper.py`、`entity_window.py` 中的语义命名，不要让同一个 GIF 在三个地方有三种完全不同的描述。

### 10.3 制作真正有区分度的 GIF

当前 state1、state4、state5 在视觉上很可能难以区分（都是 8 帧、~120KB、9.1fps 的简单动画）。建议：
- 为每个状态制作**视觉上有明显差异**的 GIF
- 不同状态应有不同的动作、颜色调性或特效
- 考虑让 state3 以外的 GIF 也使用更高帧率/更多帧数

## 十二、最终结论

1. **你的感觉是对的**：除了空闲入侵和轨迹登场，其他效果在视觉上确实很相似
2. **原因**：GIF 素材本身区分度不够 + 大量状态切换依赖摄像头（你可能没启用）+ 粒子效果触发条件苛刻
3. **设置面板确实缺少**动画映射预览功能
4. **建议**：
   - 在设置面板加一个"动画状态预览"Tab
   - 统一三个文件中的 GIF 语义命名
   - 为 state1/4/5 等视觉相似的 GIF 重新制作有明显差异的动画素材
   - 考虑降低粒子效果的触发门槛，让更多场景能触发不同的视觉反馈
