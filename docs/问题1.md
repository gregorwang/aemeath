> 生成时间: 2026-02-26  
> 分析基于运行日志和源码深度 Review

## 问题一：双重空闲机制冲突

### 症状描述

系统中存在 **两套独立的空闲响应机制**，导致语义冲突和行为不可预期：

| 机制 | 触发源 | 行为 | 代码位置 |
|------|--------|------|----------|
| **Legacy Idle Summon**（旧） | `IdleMonitor.user_idle_confirmed` → `Director.on_user_idle()` | 超过阈值后自动召唤角色出现（HIDDEN→ENGAGED），同时播放语音脚本 | `director.py:333-361` |
| **Idle Invasion**（新） | `IdleMonitor.idle_time_updated` → `IdleInvasionController._on_idle_time_updated()` | 超过 `start_delay_ms` 后逐渐在屏幕上生成 GIF 入侵角色 | `idle_invasion.py:201-245` |

### 根因分析

`IdleMonitor` 同时绑定了两个消费者：

```
main.py:338  →  director.bind_idle_monitor(idle_monitor)
main.py:339  →  idle_invasion_controller.bind_idle_monitor(idle_monitor)
```

Director 的 `bind_idle_monitor` 会连接以下信号：
```python
# director.py:324-331
idle_monitor.user_idle_confirmed.connect(self.on_user_idle)
idle_monitor.user_active_detected.connect(self.on_user_active)
idle_monitor.idle_time_updated.connect(self._on_idle_time_updated)
```

IdleInvasionController 的 `bind_idle_monitor` 也连接了同样的信号：
```python
# idle_invasion.py:124-127
idle_monitor.idle_time_updated.connect(self._on_idle_time_updated)
idle_monitor.user_active_detected.connect(self._on_user_active)
```

**关键点**：`on_user_idle()` 内部虽然已经有一个"如果 idle_invasion 已启用则跳过"的守卫：

```python
# director.py:353-358
if bool(getattr(getattr(self._config, "idle_invasion", None), "enabled", False)):
    self.LOGGER.info("[IdleBehavior] Legacy idle summon skipped: idle_invasion enabled")
    if self._idle_monitor is not None:
        self._idle_monitor.reset_to_standby()
        self._arm_idle_threshold_with_jitter()
    return
```

**但问题在于**：

1. **两者共用同一个 `IdleMonitor` 阈值**。`Director.bind_idle_monitor()` 中调用了 `self._arm_idle_threshold_with_jitter()` 来设置 `idle_monitor` 的阈值。当 Legacy idle summon 触发并被跳过时，它会 `reset_to_standby()` + 重新 `arm_idle_threshold_with_jitter()`，**频繁重置 IdleMonitor 状态**，这可能干扰 IdleInvasionController 对空闲时间的连续追踪。

2. **`_prolonged_idle_timer`（第三个空闲响应）** 也在发挥作用！`director.py:251-255` 定义了一个 10 分钟单次定时器：
   ```python
   self._prolonged_idle_timer = QTimer(self)
   self._prolonged_idle_timer.setSingleShot(True)
   self._prolonged_idle_timer.setInterval(10 * 60 * 1000)  # 10 minutes
   self._prolonged_idle_timer.timeout.connect(self._on_prolonged_idle)
   ```
   它在角色进入 HIDDEN 状态时启动（`director.py:796`），每 10 分钟触发一次 `on_prolonged_idle()`，会生成"思考/发呆"GIF 粒子（`gif_state_mapper.py:165-180`）。**这是第三个空闲相关行为**，与日志中提到的"三分钟发呆"可能相关。

### 冲突场景复现

```
[08:56:07] Application starting
[08:56:07] [DevMode] FAST_IDLE enabled: idle_threshold=60s start_delay=60000ms
```

在 Dev Fast Idle 模式下：
- `idle_threshold_seconds = 60s` → IdleMonitor 60 秒后触发 `user_idle_confirmed`
- `idle_invasion.start_delay_ms = 60000ms` → IdleInvasion 也在 60 秒后开始入侵

两者几乎同时触发，形成竞争条件。

### 建议修复方案

**保留 Idle Invasion，移除 Legacy Idle Summon**：

1. **将 `Director.on_user_idle()` 简化**：当 `idle_invasion.enabled` 为 `True` 时，完全跳过，不再做 `reset_to_standby()` 和 `arm_idle_threshold_with_jitter()`，避免干扰 IdleInvasion 的空闲计时。

2. **评估 `_prolonged_idle_timer` 的存废**：
   - 如果 Idle Invasion 已经覆盖了空闲时的视觉效果，那么 `_prolonged_idle_timer` 触发的"思考粒子"是重复的，应移除。
   - 如果希望保留"思考粒子"作为 Idle Invasion 之外的补充效果，需要确保不会与 Idle Invasion 的 GIF 冲突。

3. **最好是 `Director.bind_idle_monitor()` 里不再连接 `user_idle_confirmed`**（或至少在 idle_invasion 启用时不连接），让空闲行为完全由 `IdleInvasionController` 接管。

## 问题二：语音召唤链路延迟分析

### 完整调用链路

从日志可以还原出 Ctrl+B push-to-talk 的完整链路：

```
用户按下 Ctrl+B
    ↓
HotkeyManager 捕获全局热键 (hotkey_manager.py:52)
    ↓ QTimer.singleShot(0, self._on_push_to_talk)
VoiceRuntimeController.start_push_to_talk_once() (voice_runtime.py:83)
    ↓ 通知 "开始收音，请说话…"
    ↓ 启动 threading.Thread(_worker)
    ↓
    ├── step 1: 创建 VoiceWakeupListener 临时实例 (voice_wakeup.py:823-875)
    ├── step 2: 打开麦克风并校准噪音 (0.5s)
    ├── step 3: recognizer.listen(timeout=6s, phrase_time_limit=12s) — 等待语音输入
    ├── step 4: audio.get_wav_data(convert_rate=16000) — 将音频转为 WAV
    ├── step 5: 发送给远程 ASR API (WebSocket/HTTP)   ← ★★★ 主要瓶颈
    │   ├── openai_whisper: HTTP POST wav 文件，timeout=20s
    │   ├── xai_realtime: WebSocket 连接，发送 PCM16 base64，timeout=25s
    │   └── zhipu_asr: HTTP POST wav 文件，timeout=20s
    ├── step 6: 解析返回的文本
    ↓
    ↓ Signal → _ptt_bridge.result.emit(text)
VoiceRuntimeController._on_ptt_result(text) (voice_runtime.py:124)
    ↓ 日志 "[PushToTalk] transcript=..."
    ↓ 通知用户识别结果
    ↓
_execute_voice_command(text, source="push_to_talk") (main.py:448)
    ↓ VoiceCommandMatcher.match(text, min_score=66)
    ↓ 日志 "[VoiceCommand] matched source=push_to_talk action=summon ..."
    ↓
_summon_now_or_notify("voice:push_to_talk") (main.py:366)
    ↓
Director.summon_now() (director.py:574)
    ↓ transition_to(EntityState.ENGAGED)
    ↓ _enter_engaged() → 播放语音 → 开启摄像头
    ↓ 日志 "[FSM] 状态转换: HIDDEN -> ENGAGED"
```

### 各环节时间开销分析

```
[08:56:17] [Hotkey] Ctrl+B pressed              ← 用户按键
[08:56:25] [PushToTalk] transcript=小爱同学，请你出来   ← 识别完成
[08:56:25] [VoiceCommand] matched ... action=summon    ← 命令匹配
[08:56:25] [FSM] 状态转换: HIDDEN -> ENGAGED           ← 召唤完成
```

**总延迟: 8 秒**（08:56:17 → 08:56:25），其中：

| 阶段 | 估算耗时 | 说明 |
|------|----------|------|
| 麦克风初始化 + 噪音校准 | ~0.5s | `adjust_for_ambient_noise(duration=0.5)` |
| 等待用户说话 + VAD 检测 | ~2-4s | `recognizer.listen(timeout=6, phrase_time_limit=12)` 等用户开始并结束说话 |
| 音频编码 | ~0.1s | `audio.get_wav_data()` / `audio.get_raw_data()` |
| 远程 ASR 网络调用 | ~2-4s | **★ 主要瓶颈** — WebSocket 握手 + 发送音频 + 等待结果 |
| 命令匹配 + 召唤 | <0.1s | 纯内存操作 |

### 关于"MP3 打包"

日志开头出现的：
```
[mp3 @ ...] Estimating duration from bitrate, this may be inaccurate
Input #0, mp3, from '...1567c3fe58723241da0776f2acd4cae2.mp3':
```

**这不是 ASR 链路产生的**，而是 `AudioManager` 通过 `QMediaPlayer`（底层 FFmpeg）播放 TTS 合成的 MP3 缓存文件时输出的 FFmpeg 信息日志。

ASR 实际发送的是：
- **Whisper / 智谱**: WAV 格式（`audio.get_wav_data(convert_rate=16000)`）
- **xAI Realtime**: PCM16 原始数据（`audio.get_raw_data(convert_rate=16000)`），通过 WebSocket 发送

所以**慢不是因为 MP3 转码**，而是因为：
1. 网络 RTT 延迟（尤其是海外 API 如 xAI）
2. VAD（语音端点检测）等待时间
3. 每次都要初始化麦克风和校准噪音（0.5s 固定开销）

### 链路优化建议

1. **预初始化麦克风**：将 `Microphone()` 和噪音校准提前到应用启动时完成一次，push-to-talk 时复用。省约 0.5s。

2. **使用本地 ASR** 替代远程调用：如 Whisper.cpp、SenseVoice 等本地模型，可将 ASR 延迟从 2-4s 降至 0.3-0.8s。

3. **流式 ASR**：如果继续使用远程 API，考虑在录音的同时实时发送音频流（而非录完再发），可实现"说完即出结果"。

4. **快速命令模式**：对于"出来""隐藏"等短命令，可以用本地关键词检测（keyword spotting）代替 full ASR，延迟可降至 <0.5s。

## 问题三：TTS 播放触发音频检测的状态冲突

### 症状描述

从日志可以清晰看到状态抖动：

```
[08:56:25] [FSM] 状态转换: HIDDEN -> ENGAGED      ← 召唤成功
[08:56:30] [GifStateMapper] 音频检测到，开始音乐律动效果   ← ❌ TTS 播放被误检
[08:56:30] [BehaviorMode] MEDIA_PLAYING              ← ❌ 模式被切走
[08:56:32] [GifStateMapper] 音频停止，结束律动效果
[08:56:32] [BehaviorMode] IDLE
[08:56:38] [GifStateMapper] 音频检测到，开始音乐律动效果   ← ❌ 又一次误触发
[08:56:38] [BehaviorMode] MEDIA_PLAYING
[08:56:39] [GifStateMapper] 音频停止，结束律动效果
[08:56:39] [BehaviorMode] IDLE
[08:56:45] [GifStateMapper] 音频检测到，开始音乐律动效果   ← ❌ 再次误触发
[08:56:45] [BehaviorMode] MEDIA_PLAYING
[08:56:46] [GifStateMapper] 音频停止，结束律动效果
[08:56:46] [BehaviorMode] IDLE
```

角色被召唤后的 15 秒内，**BehaviorMode 在 IDLE ↔ MEDIA_PLAYING 之间快速抖动了 3 次**，每次持续仅 1-2 秒。

### 根因分析

#### 音频检测器选择错误

在 `main.py:312-315`：
```python
audio_output_monitor = AudioDetector(
    poll_interval_ms=200,
    threshold=0.01,
)
```

**这里使用的是 `AudioDetector`（系统音频电平检测），而不是 `AudioOutputMonitor`（WASAPI 会话级检测）！**

- `AudioDetector`：通过 COM 接口读取系统**默认渲染音频端点的 Peak Meter 电平值**。**它无法区分音频来源**——无论是浏览器播放音乐、还是本应用自己的 TTS 输出，只要系统音频峰值 > 0.01 就判定为"有音频"。

- `AudioOutputMonitor`：通过 WASAPI 的 **Audio Session 接口**枚举各进程的音频会话，并可以**按进程名/PID 过滤**。它内置了忽略 `cybercompanion`、`python`、`pythonw` 等进程的逻辑：
  ```python
  # audio_output_monitor.py:47-56
  _NON_MEDIA_PROCESS_KEYWORDS = (
      "cybercompanion", "python", "pythonw",
      "ffmpeg", "audiodg", "svchost",
  )
  ```

#### 自身播放过滤不够可靠

`Director` 有一套 `_self_playback_active` 机制来过滤自己的 TTS 播放：

```python
# director.py:909-923  _on_audio_output_started()
if self._self_playback_active:
    self.LOGGER.debug("[AudioOutputMonitor] 忽略本进程语音播放触发的音频输出")
    return
```

但问题是 **`_self_playback_active` 的开启/关闭与 `AudioDetector` 的检测存在时间差**：

1. `AudioManager._start_playback()` emit `playback_started` → `Director._on_self_playback_started()` 设置 `_self_playback_active = True`
2. 但 `AudioDetector` 是每 200ms 轮询一次系统 Peak Meter，其 debounce 需要 2 个连续"有声音"的采样点才会触发 `audio_started`（约 400ms 延迟）
3. **如果 TTS 播放到 Peak Meter 变化之间有延迟**（比如 QMediaPlayer 异步加载 MP3），`AudioDetector` 的 `audio_started` 可能在 `_self_playback_active` 还没设置之前就触发了
4. 相反，当 TTS 播放结束后，`_on_self_playback_finished()` 将 `_self_playback_active = False`，但系统 Peak Meter 可能还有残余电平（echo/尾音），导致 `AudioDetector` 再次误报

#### 时序问题图示

```
时间线 ──────────────────────────────────────────────────────►

AudioManager:  ─── emit playback_started ──── 播放 TTS ──── emit playback_finished ───
                   │                                        │
Director:     ─── _self_playback_active=True ────────────── _self_playback_active=False──
                   │                                        │
AudioDetector: ────── peak < 0.01 ── peak > 0.01 (debounce 400ms) ── emit audio_started ──
                                                            ↑
                                                     此时 self_playback_active
                                                     可能已经是 False
                                                     → 误判为外部音频！
```

### 状态抖动的连锁反应

每次误触发 `_on_audio_output_started()`：
1. `BehaviorMode` 被设为 `MEDIA_PLAYING`
2. `GifStateMapper.on_audio_started()` 被调用 → 生成"音乐律动"GIF 粒子
3. `_audio_pulse_timer` 被启动，每隔固定间隔持续生成音乐粒子

几秒后 TTS 播放结束，Peak Meter 回到 0：
1. `_on_audio_output_stopped()` 被调用
2. `BehaviorMode` 切回 `IDLE`
3. `GifStateMapper.on_audio_stopped()` 停止律动效果

**如果 TTS 有多段（如召唤台词 + 屏幕评论），这个抖动会反复发生**。

### 建议修复方案

#### 方案 A：使用 `AudioOutputMonitor` 替代 `AudioDetector`（推荐）

将 `main.py:312-315` 改为：
```python
from core.audio_output_monitor import AudioOutputMonitor

audio_output_monitor = AudioOutputMonitor(
    poll_interval_ms=500,
    ignore_current_process_audio=True,
    prefer_media_sessions=True,
)
```

`AudioOutputMonitor` 已经内置了：
- 按 PID 忽略本进程音频
- 按进程名关键词过滤非媒体进程
- 仅在真正的媒体应用（Chrome、Edge、VLC、QQ 音乐等）播放时才报告

**注意**：`AudioOutputMonitor` 和 `AudioDetector` 的信号接口是兼容的（都有 `audio_playing_started` / `audio_playing_stopped`），所以替换后 Director 的接线不需要改动。

#### 方案 B：增强 `_self_playback_active` 的时间窗口保护

如果暂时不想换组件，可以在 `_on_self_playback_finished()` 中增加一个冷却窗口：

```python
@Slot()
def _on_self_playback_finished(self) -> None:
    # 延迟 1 秒后才真正关闭过滤标记，给音频尾音消散留时间
    QTimer.singleShot(1000, self._deferred_clear_self_playback)

def _deferred_clear_self_playback(self) -> None:
    self._self_playback_active = False
    if (
        self._audio_output_reactive
        and self._audio_output_monitor is not None
        and self._audio_output_monitor.is_playing
    ):
        self._on_audio_output_started()
```

#### 方案 C：在 `AudioDetector` 中增加 PID 过滤

给 `AudioDetector` 增加类似 `AudioOutputMonitor` 的进程级过滤逻辑。但这会显著增加 `AudioDetector` 的复杂度，不如直接用已有的 `AudioOutputMonitor`。

## 总结：修复优先级

| 优先级 | 问题 | 修复方案 | 预计影响 |
|--------|------|----------|----------|
| 🔴 P0 | TTS 触发音频检测导致状态抖动 | 用 `AudioOutputMonitor` 替换 `AudioDetector` | 消除所有 MEDIA_PLAYING 误触发 |
| 🟠 P1 | Legacy idle summon 与 Idle Invasion 竞争 | 在 `idle_invasion.enabled` 时完全跳过 `on_user_idle` 并不重置 IdleMonitor | 消除空闲状态的双重触发 |
| 🟡 P2 | `_prolonged_idle_timer` 可能与 Idle Invasion 重复 | 评估是否移除；若保留需设互斥 | 减少视觉干扰 |
| 🟢 P3 | 语音召唤链路 8 秒延迟 | 短期：预初始化麦克风；中期：本地 ASR | 体验显著改善 |
