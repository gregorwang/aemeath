## 1. 产品当前问题总览

### 关键发现

| # | 问题 | 分类 | 当前动作 |
|---|------|------|---------|
| 1 | 空闲入侵开着，角色不说台词 | 核心体验 | 需拆分处理（见方案二附带说明） |
| 2 | 台词只有 3 条，用户不能自定义 | 内容缺失 | **本次实施** |
| 3 | 屏幕解读与角色出场没联动 | 体验割裂 | **本次实施** |
| 4 | 语音不能对话，只能下命令 | 功能受限 | 搁置（大模型延迟过高） |
| 5 | 没有请勿打扰模式 | 功能缺失 | **本次实施** |
| 6 | 出错后没有明确的用户引导 | 体验缺失 | **本次实施** |
| 7 | 新用户不知道怎么玩 | 引导缺失 | **本次实施** |
| 8 | 无人脸提醒对着空气说话 | 逻辑不合理 | **本次实施** |
| 9 | 悲伤安慰只有一句话 | 体验粗糙 | 搁置（后续补充） |
| 10 | 心情不持久化 | 功能缺失 | 搁置（后续优化） |
| 11 | 设置面板太技术化 | 体验问题 | 搁置（后续优化） |
| 12 | 用户指南只面向开发者 | 文档缺失 | 通过方案五解决 |

### 关于大模型对话的说明

> 目前大模型（xAI / DeepSeek）请求延迟过高（往返 2~8 秒），不适合做实时语音对话。当前大模型仅用于**屏幕内容识别 → 生成评论 → TTS 播放**，这个链路可以接受 3~5 秒延迟。自由对话需要等本地小模型方案成熟后再考虑，目前不纳入计划。

### 关于"降级策略"的原则

> 本项目不做静默降级。出错了就是出错了 — 弹提示告诉用户发生了什么、怎么反馈。不要自作主张帮用户做决定（比如自动切到离线模式），用户会困惑"我的功能为什么突然不能用了"。

## 2. 方案一：台词自定义面板

### 需求描述

用户希望能自定义角色说的台词，而不仅仅依赖内置的 scripts.json。

### 产品方案

#### 入口

在现有的 **设置面板** 中新增一个 Tab 页——**「台词管理」**。

#### 界面设计

│  ├───┼─────────────────────┼────────┼─────┤    │
│  │ 1 │ 三分钟没动了，发呆吗？ │ 全天   │ ✏️ 🗑 │    │
│  │ 2 │ 这么晚了还不睡...     │ 22-06  │ ✏️ 🗑 │    │
│  │ 3 │ 不去吃饭代码要降30%   │ 12-13  │ ✏️ 🗑 │    │
│  │ + │ [ 添加新台词 ]        │        │     │    │
│  └─────────────────────────────────────────┘    │
│                                                 │

│  │ # │ 台词内容             │ 操作         │    │
│  ├───┼─────────────────────┼──────────────┤    │
│  │ 1 │ 哇！被发现了！        │ ✏️ 🗑        │    │
│  │ 2 │ 才没有在偷看你...     │ ✏️ 🗑        │    │

#### 添加 / 编辑弹窗

点击「添加新台词」或编辑按钮时弹出：

```
┌────────────────────────────────────┐
│ 编辑台词                           │
├────────────────────────────────────┤
│ 台词内容:  [__________________ ]   │

│           可选: 全天 / 22:00-06:00 │

```

#### 数据存储

- 用户自定义的台词保存在 `characters/<角色id>/scripts.json` 中，和内置台词格式完全一致
- 用户修改后直接覆写 `scripts.json`
- 提供「恢复默认台词」按钮，恢复出厂内置台词
- 台词修改后立即生效（调用 `ScriptEngine.refresh()`），无需重启

- 保存时写入对应角色目录的 `scripts.json`
- 通过 `AssetManager.reload()` + `ScriptEngine.refresh()` 热更新

## 3. 方案二：屏幕解读与角色出场联动

### 需求描述

当触发屏幕解读时（无论手动还是自动），角色应该先**出现在屏幕上**，然后再开始说话。目前屏幕解读和角色出场是两个独立的行为，可能出现"角色没出来但已经在讲话"的情况。

### 产品方案

#### 场景梳理

| 触发方式 | 触发时角色状态 | 期望行为 |
|---------|-------------|---------|
| 右键菜单「你在看什么？」 | 角色已出场 | 直接解读，角色切到"思考"表情 |
| 右键菜单「你在看什么？」 | 角色隐藏 | 先召唤角色出场 → 等出场动画完毕 → 开始解读 |
| 托盘菜单「你在看什么？」 | 角色隐藏 | 先召唤角色出场 → 等出场动画完毕 → 开始解读 |
| 语音命令「看屏幕」 | 角色隐藏 | 先召唤出场 → 解读（当前已有此逻辑，需确认链路可靠） |
| 自动定时解读 | 角色隐藏 | 先召唤角色出场 → 解读 → 解读完后按正常自动消失逻辑退场 |
| 自动定时解读 | 角色已出场 | 直接解读 |

#### 联动流程

```
用户触发"屏幕解读"
        │
        ▼
  角色当前可见？ ──是──→ 切到 state5（思考状态）
        │                     │
       否                     ▼
        │               开始屏幕解读
        ▼
  summon_now() 召唤角色出场
        │
        ▼
  等角色出场动画完成（约 800ms）
        │
        ▼
  切到 state5（思考状态）
        │
        ▼
  开始屏幕解读（截屏 → LLM → TTS 播放）
        │
        ▼
  解读完毕 → 切回 state1
        │
        ▼
  重新开始自动消失倒计时
```

#### 关键技术变更

**`Director.request_screen_commentary()`** 方法需要修改：

1. 在方法开头检查 `self._state_machine.current_state == EntityState.HIDDEN`
2. 如果是 HIDDEN：先调用 `self.summon_now()` 召唤
3. 使用 `QTimer.singleShot(800, ...)` 等出场动画完成后再启动 commentary
4. 如果角色已经可见，直接开始解读（维持现有逻辑）

**自动定时解读 (`_on_auto_screen_commentary_timeout`)** 也要同样处理：
- 现在的逻辑是全屏时跳过，但隐藏时不管 → 改为：隐藏时先召唤

#### 边界情况

- 解读过程中用户操作触发 `on_user_active()` → 正在解读的 TTS 应继续播完（不打断），但角色的 flee 动画和 panic 台词要正常执行
- 连续快速点击 → 用 `_screen_commentary_active_count` 防重入（已有）

## 4. 方案三：请勿打扰模式

### 需求描述

用户在开会、共享屏幕、做演示时，不希望角色突然弹出来。

### 产品方案

#### 入口（三个入口保持一致）

1. **托盘菜单**：新增「🔕 请勿打扰」菜单项（可切换 ✓/无勾）
2. **右键角色菜单**：同上
3. **全局快捷键**：沿用 `Ctrl+Shift+D`（D = Do not Disturb）

#### 行为定义

开启「请勿打扰」后：

| 功能 | 是否暂停 | 说明 |
|------|---------|------|
| 空闲自动出场 | ✅ 暂停 | 不会主动探头 |
| 空闲入侵 | ✅ 暂停 | 小人不会爬出来 |
| 自动屏幕解读 | ✅ 暂停 | 不会定时截屏解读 |
| 手动召唤（Ctrl+Shift+S） | ❌ 正常 | 用户主动召唤不受限 |
| 手动屏幕解读 | ❌ 正常 | 用户手动触发不受限 |
| 语音命令 | ❌ 正常 | 用户主动交互不受限 |
| TTS 语音输出 | ❌ 正常 | 仅手动触发的才会播 |

**核心原则**：请勿打扰 = 禁止所有**自动/被动**行为，保留所有**用户主动触发**行为。

#### 持久化

- DND 状态**不写入 config.json**，仅在本次会话有效
- 重启应用后 DND 自动关闭
- 原因：DND 是临时行为（开会结束就应该恢复），不应该永久生效导致用户忘记

#### 视觉提示

- 开启 DND 后，托盘图标 tooltip 改为 `"Cyber Companion (请勿打扰)"`
- 开启/关闭时弹出一个短暂的系统通知：`"请勿打扰：已开启"` / `"请勿打扰：已关闭"`

#### 技术要点

- `Director` 新增 `_dnd_mode: bool` 字段
- `on_user_idle()` 开头加判断：`if self._dnd_mode: return`
- `IdleInvasionController._on_idle_time_updated()` 需要接受 DND 状态
- `_on_auto_screen_commentary_timeout()` 开头加判断
- `tray_icon.py` 新增可勾选菜单项

## 5. 方案四：错误提示与用户反馈引导

### 需求描述

当应用出错时（API 调用失败、摄像头打不开、TTS 失败等），不要静默降级，要**明确告诉用户发生了什么**，并引导用户如何反馈问题。

### 产品方案

#### 通用错误提示模板

所有运行时错误统一用以下模板通知用户：

```
┌──────────────────────────────────────┐
│  ⚠ [功能名] 出错了                    │
│                                      │
│  [一句话描述问题]                      │
│                                      │
│  请提交 Bug 报告:                     │
│  🔗 https://github.com/xxx/issues    │
│                                      │
│  请附带日志文件最后 50 行:             │
│  📂 打开日志目录                      │
│  📋 一键复制最近日志                   │
└──────────────────────────────────────┘
```

#### 各功能错误提示文案

| 功能 | 文案 |
|------|------|
| 屏幕解读 LLM 调用失败 | `"屏幕解读失败：AI 模型无法连接。请检查网络并在设置中确认 API Key。"` |
| TTS 语音失败 | `"语音合成失败：请检查网络连接。"` |
| 摄像头打不开 | `"摄像头无法启动：请确认摄像头未被其他程序占用。"` |
| 语音识别失败 | `"语音识别失败：请检查麦克风和 ASR 配置。"` |
| 配置文件保存失败 | `"设置保存失败：请检查文件权限。"` |

#### 反馈引导 — 两个入口

1. **每次错误通知中附带链接**（见上方模板）
2. **托盘菜单 / 右键菜单新增**：`"反馈问题"` 菜单项
   - 点击后打开默认浏览器跳转到 `https://github.com/用户名/aemeath/issues/new`
   - 或跳转到飞书 Bug 报告文档链接

#### "一键复制最近日志"功能

提供一个按钮/菜单项：**「复制最近日志」**

- 读取 `app.log` 文件的最后 50 行
- 自动复制到系统剪贴板
- 弹通知 `"已复制最近 50 行日志到剪贴板"`
- 用户粘贴到 GitHub Issue 或飞书文档中即可

#### 技术要点

- 新建 `core/error_handler.py`，统一管理错误提示和反馈引导
- 提供 `show_error(feature: str, message: str)` 方法
- 反馈 URL 从 `config.json` 读取或硬编码为常量
- 剪贴板操作用 `QApplication.clipboard().setText(...)`
- log 读取用 `Path(log_file).read_text().splitlines()[-50:]`

## 6. 方案五：新用户引导

### 需求描述

新用户安装后不知道怎么玩，功能太多，入口不明显。

### 产品方案

#### 方案：首次启动打开 GitHub README

**最简洁有效的做法**：

1. 在 `config.json` 中新增字段 `"first_run": true`
2. 应用首次启动时检测到 `first_run == true`：
   - 弹出系统通知：`"欢迎使用赛博伴侣！正在打开使用指南..."`
   - 调用 `webbrowser.open("https://github.com/xxx/aemeath#使用指南")` 打开浏览器
   - 将 `first_run` 设为 `false` 并保存
3. 后续启动不再弹出

#### GitHub README 中需要包含的内容

在 README.md 中新增一个 **「快速上手」** 章节：

```markdown
## 🎮 快速上手

### 角色会自己出来
安装启动后什么都不用做，空闲 3 分钟角色就会自动出来跟你说话。

### 怎么跟它互动
- **鼠标双击角色**：让它隐藏/出现
- **右键角色**：打开功能菜单（屏幕解读、设置等）
- **右键托盘图标**：更多功能入口

### 快捷键
| 快捷键 | 功能 |
|--------|------|
| Ctrl+Shift+S | 立即召唤角色 |
| Ctrl+Shift+D | 请勿打扰模式 |

### 设置入口
右键托盘图标 → 设置，可以配置：
- AI 功能（需要 API Key）
- 摄像头和语音
- 空闲入侵参数
- 自定义台词
```

#### 为什么不做应用内引导

- 目前产品还在调试阶段，功能还在变动，做引导页面会增加维护成本
- GitHub 的 MD 文档可以随时更新，用户看到的永远是最新版
- 用户群体是技术向的，能接受阅读文档

#### 技术要点

- `config_manager.py` 的 `BehaviorConfig` 新增 `first_run: bool = True`
- `main()` 中启动后判断 `config.behavior.first_run`，`True` 时打开浏览器并置 `False`
- URL 可以设为常量，方便后续改为正式文档网站

## 7. 方案六：无人脸提醒改造

### 当前问题

现在的逻辑是：角色已经出场（可见状态），摄像头连续 3 秒检测不到人脸 → 角色说"我暂时看不到你，等你回来"。

**问题**：用户离开了座位（人不在），对着空气说话没有意义。

### 改造方案

**改为「回来时的问候」**：

#### 新逻辑

```
角色可见时 + 摄像头连续 3 秒没检测到人脸
        │
        ▼
  记录"离开时间"（不说话，只标记）
        │
    用户回来了（摄像头重新检测到人脸）
        │
        ▼
  计算离开了多久
        │
        ├── < 30 秒：不说话（可能只是转头看别的地方了）
        │
        ├── 30 秒 ~ 5 分钟：说一句短的
        │   "回来啦~"
        │
        ├── 5 ~ 30 分钟：说一句中等的
        │   "你去了 X 分钟哦，我在这等你呢。"
        │
        └── > 30 分钟：说一句长的
            "你离开了好久！去做什么了？"
```

#### 数据字段

- `_user_left_at: float | None` — 标记用户离开的时间（`time.monotonic()`）
- `_user_away_notified: bool` — 防止重复触发

#### 回来问候的台词池

```python
SHORT_RETURN_TEXTS = ["回来啦~", "欸你回来了。"]
MEDIUM_RETURN_TEXTS = ["你去了{minutes}分钟哦，我一直在等你呢。", "去了{minutes}分钟，还以为你把我忘了。"]
LONG_RETURN_TEXTS = ["你离开了好久！去做什么了？", "终于回来了！我都快睡着了。"]
```

#### 技术要点

- 修改 `_maybe_trigger_no_face_test()` → 改为 `_maybe_mark_user_away()`
  - 不再即时说话，只记录 `_user_left_at = time.monotonic()`
- 在 `_on_gaze_updated()` 中检测：如果 `_user_left_at` 不为 None 且人脸重新出现
  - 计算离开时长
  - 根据分档选择台词
  - TTS 播放后清除标记
- 冷却逻辑保留，避免用户反复站起来坐下导致刷屏

## 8. 暂时搁置的问题

### 8.1 空闲入侵与角色说话互斥

**当前状态**：空闲入侵开启（默认）时，空闲触发的角色出场（探头+说台词）被跳过。

**暂时搁置原因**：这确实是核心体验问题，但修改涉及 `Director.on_user_idle()` 和 `IdleInvasionController` 的协调关系，改动较大。

**后续方向**：让两者共存 —— 空闲 3 分钟 → 角色先出场说话 → 持续空闲 5 分钟 → 入侵开始。Director 的空闲触发不应该被 invasion.enabled 跳过，而是 invasion 应该有自己的更长的延迟。

### 8.2 语音对话能力

**当前状态**：用户只能说固定指令，不能自由聊天。

**暂时搁置原因**：大模型延迟太高（3~8 秒），做不到实时对话体验。等本地小模型（如 Qwen3-TTS、GLM-5B-ASR）端到端延迟可控在 1 秒内再考虑。

> 💡 **中期方向**：可以做"延迟对话" — 用户说了话之后，角色先回一句"让我想想..."（固定台词快速响应），然后后台请求 LLM，拿到结果后再 TTS 播报。这样用户感知到"它在思考"而不是"它死了"。

### 8.3 悲伤安慰台词太少

**当前状态**：只有一句"别难过"。

**后续方向**：
- 扩充到 5~6 句不同的安慰语，随机选择
- 安慰后进入"陪伴模式"（state5），多停留 1 分钟
- 如果有 LLM 可用，调用 LLM 生成个性化安慰语

### 8.4 心情不持久化

**当前状态**：每次重启心情值回到 0.5。

**后续方向**：在 `config.json` 或 `user_state.json` 中保存心情值，启动时加载。

### 8.5 设置面板对普通人太硬核

**当前状态**：所有设置平铺展示，包含 ASR 温度、流式分段字数等技术参数。

**后续方向**：
- 设置面板分为「基础」和「高级」两层
- 基础页只展示：音量、空闲时间、位置、请勿打扰
- 高级页折叠展示：API 配置、ASR 参数、入侵细节

### 方案一：台词自定义面板

**结论：⚠️ 中等偏高 — 建议简化**

| 维度 | 分析 |
|------|------|
| 改动文件 | `settings_dialog.py`（760 行，已经很长）、`asset_manager.py`、`main.py` |
| 核心难点 | 1. `settings_dialog.py` 需要新增 ~200 行的 Tab 页代码（QTableWidget + 弹窗编辑器）<br>2. 需要知道"当前活动角色的目录"才能读写 scripts.json，但 settings_dialog 目前不持有角色目录路径<br>3. 保存台词后需要触发 `AssetManager` 重新加载 + `ScriptEngine.refresh()`，但这两个对象在 main.py 里，不在 dialog 里 |

4. 加一个 **「重载台词」** 按钮，调用 `AssetManager._load_scripts()` + `ScriptEngine.refresh()`

**改动量**：
- `tray_icon.py`：加 2 个菜单项（编辑台词 + 重载台词），~10 行
- `main.py`：加 2 个回调函数，~20 行
- `asset_manager.py`：加一个 `reload()` 公开方法（内部就是再次调用 `_load_scripts()`），~5 行
- 总计 ~35 行改动

**对比**：完整 GUI 编辑器 ~300 行 vs 打开文件编辑器 ~35 行。功能效果一样，因为 scripts.json 格式已经很易读了。

### 方案二：屏幕解读与角色出场联动

**结论：✅ 简单可做**

| 维度 | 分析 |
|------|------|
| 改动文件 | 仅 `director.py` 的 `request_screen_commentary()` 方法 |

**具体改动**：

```python
# director.py - request_screen_commentary() 方法开头加：
def request_screen_commentary(self, *, source: str = "manual") -> None:
    # ...existing checks...
    
    # 新增：如果角色隐藏，先召唤出来
    if self._state_machine.current_state == EntityState.HIDDEN:
        if not self.summon_now():
            self.LOGGER.warning("[ScreenCommentary] Cannot summon entity, skipping")
            return
        # 等出场动画完成后再解读
        QTimer.singleShot(800, lambda s=source: self._do_screen_commentary(source=s))
        return
    
    # 角色已可见，直接解读
    self._do_screen_commentary(source=source)
```

把现有的 commentary 启动逻辑提取成 `_do_screen_commentary()`，原来的代码几乎不动，只是包了一层。

**改动量**：~15 行，纯逻辑重排，无新依赖。

**有一个边界要注意**：`summon_now()` 里会触发 `_enter_engaged()` 里的台词播放，如果解读发言和出场台词撞车，需要在解读前加 `self._suppress_engaged_script_once = True` 来跳过出场台词。这一行已经有成熟的用法（`_enter_passive_companion` 里用过），直接复用即可。

### 方案六：无人脸提醒改造

**结论：⚠️ 中等 — 可做但要注意和现有摄像头逻辑的耦合**

| 维度 | 分析 |
|------|------|
| 改动文件 | 仅 `director.py` |
| 核心改动 | 改 `_maybe_trigger_no_face_test()` 和 `_on_gaze_updated()` 方法 |
| 风险 | 中等 — 和表情追踪、被动陪伴模式等逻辑交织 |

**具体分析**：

现有的 `_maybe_trigger_no_face_test()` 逻辑（1076-1102 行）很清晰：
- 检测脸是否消失 → 记录 `_no_face_absent_since` → 超过 3 秒 → TTS

改成"回来问候"需要：
1. 原来的 `_no_face_absent_since` 改含义为"用户离开时间"
2. `_trigger_no_face_test()` 去掉（不再主动说话）
3. 在 `_on_gaze_updated()` 中加检测：脸重新出现 + `_user_left_at` 不为 None → 计算时长 → 选台词 → TTS

**复杂点在于**：`_on_gaze_updated()` 已经做了 5 件事（更新 gaze_data、刷新 presence、检查无人脸、追踪表情、触发悲伤安慰），再加"回来问候"会使这个方法更臃肿。

**简化建议**：

不改函数结构，只修改 `_maybe_trigger_no_face_test()` 和 `_trigger_no_face_test()` 的行为：

```python
# 改名但不提取新函数，减少改动量
def _maybe_trigger_no_face_test(self, gaze_data: GazeData) -> None:
    # ...现有的前置检查保持不变...
    
    if gaze_data.face_detected:
        # 脸回来了，检查是否要说"回来啦"
        if self._no_face_absent_since is not None:
            away_seconds = time.monotonic() - self._no_face_absent_since
            self._reset_no_face_tracker()
            if away_seconds >= 30:  # 至少离开30秒才说话
                self._greet_user_return(away_seconds)
        else:
            self._reset_no_face_tracker()
        return
    
    # 脸消失了，记录时间（不说话）
    if self._no_face_absent_since is None:
        self._no_face_absent_since = time.monotonic()

def _greet_user_return(self, away_seconds: float) -> None:
    if time.monotonic() - self._last_no_face_test_at < self.NO_FACE_TEST_COOLDOWN_SECONDS:
        return
    self._last_no_face_test_at = time.monotonic()
    minutes = int(away_seconds / 60)
    if away_seconds < 300:
        text = random.choice(["回来啦~", "欸你回来了。"])
    elif away_seconds < 1800:
        text = f"你去了{minutes}分钟哦，我一直在等你呢。"
    else:
        text = random.choice(["你离开了好久！去做什么了？", "终于回来了！我都快睡着了。"])
    self._audio_manager.speak(text, priority=AudioPriority.HIGH)
```

**改动量**：~30 行。改动集中在两个方法内，不影响其他功能。

**风险点**：用户快速离开/回来（比如转头看手机 3 秒又回来）会被误判为"离开"。30 秒的阈值能过滤掉大部分误判，但如果摄像头本身检测不稳定（低光照），可能偶尔误触发。可接受，不是阻塞问题。

## 11. 未来规划储备池 (v2.0+)

> 以下功能面向更成熟的 C 端产品体验，作为后续演进的技术和产品储备。

### 11.1 隐私与安全机制 (Privacy & Security)
*   **隐私声明提醒**：首次使用必须向用户明确“摄像头图像仅在本地内存处理（不保存不上云），屏幕截图仅发送至用户自行配置的 API”。
*   **场景黑名单/白名单**：当系统焦点在特定进程（如 1Password、特定无痕浏览器、或者通过黑名单正则匹配的窗口）时，**自动暂停屏幕截图和解读**功能，防止隐私和密码泄露。

### 11.2 互动历史留存 (Interaction History)
*   **最近消息面板**：目前 TTS 语音播报一闪而过。计划在托盘增加「📜 最近互动」面板，记录角色最近的 10~20 条发言（如“21:05 - 这里有个报错，别忘了查一下”），提供异步查看陪伴情绪的能力。

### 11.3 性能与功耗感知 (Battery & Eco Mode)
*   **笔记本节能模式**：桌面宠物加摄像头轮询是耗电大户。未来通过调用系统 API 获取电源状态，当检测到**笔记本未连接电源**时，自动降低视觉模块（Mediapipe）帧率、停止空闲入侵逻辑，或者暂时关闭特定后台任务，并在托盘提示“已开启节能陪伴模式”。

### 11.4 API 精细化错误提示与成本感知 (Cost Awareness)
*   **精准报错定位**：区分“网络不通”、“401 密钥错”和“402 欠费/频控限制”。当大模型返回余额不足或频控时，直接给出直白提示甚至充值指引，而不是笼统的网络错误。
*   **使用量看板（长期）**：在高级设置中隐晦地展示“本次会话共帮您进行了 5 次屏幕解读”，让用户对自己消耗的 Token 量有预期。

### 11.5 更新分发机制 (Distribution & Updates)
*   **AI 沉浸式提醒更新**：告别生硬的系统弹窗更新。通过调用 GitHub Releases 接口，如果有新版本，角色会在合适时机说出一句特殊的台词：“开发者似乎给我注入了新的灵魂（v1.1版本），你要帮我升级吗？”，并将下载链接推送到剪贴板或准备在托盘中。

### 11.6 全屏免打扰自动判定 (Auto DND)
*   **游戏/全屏检测**：现在的“请勿打扰”需要手动开启。后续集成对系统全屏应用（DirectX/OpenGL 独占全屏或全屏视频）的自动检测。当用户在打游戏或看电影时，角色自动隐藏进入勿扰，退出全屏后自动恢复。
