详细分析：GIF 状态管理与"你在看什么"触发流程
一、你看到的现象的原因
当你在托盘里点击"你在看什么"时，日志显示了如下事件链：

[ScreenCommentary] Hidden state detected, summoning first source=tray
[BehaviorMode] IDLE
[FSM] 状态转换: HIDDEN -> ENGAGED
[ScreenCommentary] Requested source=tray
[ScreenCommentary] Session start...
这里触发了一个瀑布式的连锁反应，我来逐步拆解：

二、系统中存在的三套并行状态系统
这是问题的核心——你的应用里其实有 三套独立运行、互相影响的状态系统：

🔵 第 1 套：

StateMachine
（FSM 状态机）
管理角色的生命周期状态：

HIDDEN → PEEKING → ENGAGED → FLEEING → HIDDEN
这是角色"在不在屏幕上"的基础状态。

🟢 第 2 套：

BehaviorMode
（行为模式）
管理角色"在屏幕上时的行为表现"：

IDLE → BUSY → MEDIA_PLAYING → SUMMONING
每个模式映射到一个不同的 GIF：

BehaviorMode	GIF显示
IDLE	state1.gif (好奇/探头)
BUSY	state4.gif (害羞/逃跑)
MEDIA_PLAYING	state3.gif (律动/音乐)
SUMMONING	state6.gif (开心/打招呼)
🟡 第 3 套：

GifStateMapper
（GIF 粒子系统）
管理浮游粒子 GIF 特效。这些是独立的透明小窗口，从屏幕边缘飞入的装饰效果。它和主角色窗口完全独立，可以同时生成多个。

三、"你在看什么"触发后的完整事件链
你点击"你在看什么"
  │
  ├─→ ① request_screen_commentary(source="tray")
  │     │
  │     ├─→ 检测到 current_state == HIDDEN
  │     │     → 调用 summon_now()
  │     │       → _set_behavior_mode(IDLE)         ← 🟢 BehaviorMode 变化
  │     │       → FSM: HIDDEN → ENGAGED              ← 🔵 FSM 状态变化
  │     │
  │     │   FSM 状态变化信号触发:
  │     │     → _on_state_changed_for_particles()
  │     │       → gif_state_mapper.on_engaged()    ← 🟡 生成 2 个 excited 粒子 GIF！
  │     │
  │     ├─→ 接着调用 _set_entity_state("state5")  ← 🟢 主角色换成 思考GIF
  │     │
  │     ├─→ 启动 ScreenCommentary worker
  │     │     → 截屏 → 发送给 LLM → 失败(401)
  │     │     → 触发 fallback TTS: "我这次没看清你的屏幕"
  │     │       → 播放语音
  │     │         → AudioDetector 检测到音频输出！
  │     │           → _on_audio_output_started()
  │     │             → 🟡 gif_state_mapper.on_audio_started()
  │     │               → 生成 2 个 music_vibe 粒子 GIF！
  │     │               → 启动 4 秒定时器持续生成音乐粒子！
  │     │             → 🟢 BehaviorMode → MEDIA_PLAYING
  │     │               → 主角色切换到 state3.gif (律动)
  │     │
  │     └─→ 语音播放完毕
  │           → _on_audio_output_stopped()
  │             → 🟡 gif_state_mapper.on_audio_stopped()
  │             → 🟢 BehaviorMode → IDLE
  │               → 主角色切回 state1.gif
四、你看到"好几个大GIF"的原因
那些"大GIF"不是同一个主角色窗口，而是 

GifParticleManager
 管理的独立粒子窗口。每个粒子都是一个独立的 QWidget（透明窗体），从屏幕边缘飞入。

具体地，在上述流程中至少产生了：

触发时机	触发函数	生成的粒子数	GIF 类型	scale
FSM → ENGAGED	

on_engaged()
2 个	state2.gif (兴奋)	0.5
TTS 播放（音频检测触发）	

on_audio_started()
2 个	state3.gif (律动)	0.7
音频脉冲定时器	

_on_audio_pulse()
1 个/4秒	随机 state3/state7	0.4-0.8
所以在极短时间内，最多同时可能有 4-5 个粒子 GIF 窗口 在屏幕上飞，而且 scale=0.7 已经挺大了。

五、"最左侧有一个 GIF 不动"的原因
那个不动的 GIF 很可能是以下情况之一：

主角色窗口本身 (

EntityWindow
)：它在 summon 后被 

_apply_behavior_mode_visual()
 切换了 GIF，但位置在屏幕边缘的 

full
 位置（角色的固定显示位置）。

一个粒子到达了目标位置后停着不动：粒子的生命周期是 进入动画 → 停留(linger) → 退出动画，在 linger 阶段它是静止的。如果 target="center" 但粒子飞到了边缘位置，看起来就像"不动"。

六、你说的"复杂状态叠加"——确实很复杂
这个系统存在以下设计复杂性问题：

❌ 问题 1：三套状态系统没有统一调度

StateMachine
、

BehaviorMode
、

GifStateMapper
 各自独立运行
它们通过信号互相触发，但没有一个中心调度器来协调
导致一次操作会像多米诺骨牌一样三套系统串联触发
❌ 问题 2：音频检测的"事件风暴"
TTS 播放时，AudioDetector 检测到系统音频 → 触发 MEDIA_PLAYING
虽然有 _self_playback_active 标记来过滤自身播放，但从日志看这个过滤没生效（可能是 TTS 播放信号和音频检测信号的的时序竞争）
这导致了自己的语音回放也被当成"外部音频"处理，触发了额外的粒子效果
❌ 问题 3：视觉效果缺乏节流/互斥

on_engaged()
 和 

on_audio_started()
 可以在 1-2 秒内串行触发
没有全局的"当前正在执行屏幕评论，暂停粒子效果"的逻辑
MAX_CONCURRENT = 8 的上限太高了，对于桌面宠物来说
❌ 问题 4：

_resolve_effective_behavior_mode
 会覆盖 

_behavior_mode
python
def _resolve_effective_behavior_mode(self) -> BehaviorMode:
    if self._voice_trajectory_playing:
        return BehaviorMode.SUMMONING          # 最高优先级
    if self._audio_output_active:
        return BehaviorMode.MEDIA_PLAYING      # 第二优先级
    return self._behavior_mode                 # 实际设置值
这意味着只要 _audio_output_active=True，不管你设置了什么 

BehaviorMode
，视觉上永远显示 state3.gif(律动)，形成了一种"隐性状态覆盖"。

八、总结
你的感觉是对的——这个设计确实太复杂了。核心问题是：

三套并行状态系统（FSM + BehaviorMode + GifStateMapper）彼此通过信号松散耦合，缺少统一调度
事件连锁反应导致一个简单操作（点击"你在看什么"）触发了 5-6 个不同的状态变更和 4-5 个独立粒子窗口
音频检测把自身 TTS 播放也当成外部音频，进一步放大了效果
粒子效果没有场景感知——不管是在做屏幕评论还是用户闲置，粒子效果的触发逻辑是独立的
如果你后续想简化，关键方向是：

引入一个统一的"当前活动"概念（比如"正在做屏幕评论"期间，抑制粒子效果和音频反应）
减少 GifStateMapper 的触发入口，让它只响应真正有意义的状态变化
修复 self_playback 的检测逻辑，确保 TTS 不会触发音乐律动效果
